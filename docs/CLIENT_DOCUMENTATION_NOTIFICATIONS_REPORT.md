# ELEVAY Client Documentation Notification Report

**Author:** Manus AI  
**Audit date:** 8 September 2026, Cairo  
**Scope:** Client Documentation CRM workflows and the connected ELEVAY Client Portal/App

## Executive Summary

The Client Documentation area contains three notification systems: **staff email reminders**, **client-facing in-app/push notifications**, and **staff operational alerts generated by Client Portal actions**. The portal notification system has good structural controls: bilingual in-app records, client preference checks for push categories, a delivery outbox for staff email/push attempts, protected CRM links, and no sensitive document attachments. The reminder email system, however, has material reliability and routing gaps.

The most important finding is that the scheduled reminder helper receives short database names such as `Madonna`, `Monica`, `Mahmoud`, and `Ziad`, while its email map contains only full names such as `Madonna Adel` and `Ziad Elshurafa`. Therefore, the intended assigned paralegal and consultant are normally not resolved; reminder emails fall back to Mahmoud’s two addresses plus the mandatory Ziad Gmail recipient.[1] [2] The “new client assigned” function also accepts only two arguments, but the Client Documentation router calls it with six. As a result, the client code is currently displayed as the assignee and the actual paralegal/consultant arguments are ignored.[3] [4]

The reminder scheduler is not a durable managed schedule. It runs immediately whenever a server process starts and then repeats every 24 hours inside that process. There is no reminder ledger, idempotency key, retry queue, or overlap protection.[1] [5] In an autoscaled deployment, this creates both **missed-reminder risk** when no instance remains alive and **duplicate-send risk** when instances restart or overlap.

The requested submission-date notification contract is also incomplete. The 12-day reminder includes the client name and code but not the remaining unpaid contract amount. The first “submission confirmed” reminder is not event-driven; it is evaluated during the daily scan only when `submissionDate` exists and `expectedSubmissionDate` is absent, and it can repeat on every scheduler execution while that condition remains true.[1]

| Layer | Audience | Channels | Persistence | Current reliability |
|---|---|---|---|---|

## Staff Email Reminder Inventory

The daily reminder process loads all Client Documentation cases and documents, calculates date differences, and sends only when the difference equals the configured trigger day.[1]

| Notification | Trigger | Intended recipients | Actual recipient behavior | Message fields | Key gap |
|---|---|---|---|---|---|
| Schengen expiry — 30 days | Expiry date is exactly 30 days away | Assigned paralegal and consultant | Short names do not match the full-name email map, so delivery normally falls back to Mahmoud’s two addresses; Ziad Gmail is added globally | Client name, expiry date, days remaining, paralegal, consultant | No client code, unpaid amount, durable ledger, or retry |
| Schengen expiry — 20 days | Expiry date is exactly 20 days away | Assigned paralegal and consultant | Same fallback behavior | Client name, expiry date, urgency, paralegal, consultant | Same routing and reliability gaps |
| Embassy attestation follow-up | Exactly 15 days after the embassy email date | Assigned paralegal and consultant | Same fallback behavior | Client name, embassy email date, elapsed days, assignments | No outcome/state check; can notify even if follow-up is already complete |
| Submission deadline | Expected submission date is exactly 12 days away | Assigned paralegal and consultant | Same fallback behavior | Client name, client code, date, days remaining, assignments | **Remaining unpaid contract amount is missing** |
| Submission confirmed | `submissionDate` exists while `expectedSubmissionDate` is empty | Assigned paralegal and consultant | Same fallback behavior | Client name, client code, submission date, assignments | Not sent at the moment of update; can repeat daily; unpaid amount missing |
| Document expiry | A received document reaches 30 days before calculated expiry | Assigned paralegal and consultant | Same fallback behavior | Client name, document name, expiry date, assignments | No client code; no deduplication; date arithmetic can be timezone-sensitive |

> The code comment says the scheduler sends to the assigned paralegal **and** consultant, but the database values and email-map keys use different name formats. This is a functional routing defect, not merely a documentation issue.[1] [2]

## New Client Assignment Notifications

Client Documentation attempts to send a “New Client Assigned” email after creating a case and again when a paralegal is assigned or changed.[4] The router supplies the client name, client code, application type, marital status, paralegal, and consultant. The email function currently accepts only `clientName` and `assignedTo`; JavaScript ignores the remaining four arguments.[3]

The practical result is that the email goes to Mahmoud’s two configured addresses and the mandatory Ziad Gmail recipient, while the “Assigned To” line contains the **client code** rather than the staff member. The assigned consultant and paralegal do not receive this function’s email. The call is fire-and-forget, and a provider rejection returned as `false` is not persisted or escalated.

## Client-Facing In-App and Push Notifications

Client-facing notifications are linked to portal applications. When multiple applications belong to the same portal user, the system deduplicates by portal user before creating one notification.[6]

| CRM action | In-app notification | Push category | Conditions |
|---|---|---|---|
| Staff marks one or more documents received | “Documents received” in English and Arabic | Documents | Portal application must be linked; push requires an active Expo token and enabled push/documents preference |
| Staff updates MOFA attestation | “Document attestation update” | Documents | Same conditions |
| Staff updates embassy attestation | “Document attestation update” | Documents | Same conditions |
| Staff changes important dates | “Application dates updated” | Workflow | Same conditions |
| Staff changes workflow stage | “Application stage updated” with stage name | Workflow | Created only when the stage actually changes |
| Staff sends a client-visible message | “New message from Elevay” | Messages | Internal-only replies do not notify the client |
| Staff reviews a document | Status update or replacement-required message | Documents | `visibleToClient` must be true |

The in-app record is bilingual and remains available through the client notification endpoint, which returns up to 100 newest notifications and supports marking individual items as read.[7] Push delivery uses Expo and checks the account’s `push`, `messages`, `documents`, and `workflow` preferences before sending.[6] New portal accounts default these preferences to enabled, and clients may update them through the preferences endpoint.[7]

There are two limitations. First, the push payload uses the English title/body even when the client locale is Arabic. Second, an actual message body can be included in the push preview, potentially displaying sensitive content on a device lock screen.

## Notifications Triggered by Client Portal Actions

| Client action | Confirmation to client | Staff email | CRM shared notification |
|---|---|---|---|
| Upload or scan document | Bilingual in-app “Document received” confirmation | Consultant, paralegal, Mahmoud corporate address, and mandatory Ziad Gmail; includes document metadata and optional comment; **file is not attached** | “New client document” |
| Send message | Bilingual in-app “Message sent” confirmation | Same staff recipient policy; includes up to 500 characters of the client message | “New client message” |
| Request account deletion | API confirmation only | Same staff recipient policy; includes account identity and request time | “Client account deletion request” |

The Client Portal staff-recipient function correctly recognizes both short and full staff names and always includes Mahmoud’s corporate address; the centralized system-recipient policy adds `Ziadelshurafa@gmail.com` and removes case-insensitive duplicates.[6] [8] This routing is stronger than the separate reminder-email helper.

Staff emails are written to `client_portal_delivery_outbox` before sending, then marked `sent` or `failed` with one attempt.[6] There is currently no worker that retries failed rows. CRM notification-center events are written to a shared `systemNotifications` table without a user recipient column, so they appear in the common notification feed rather than being individually addressed.[9]

## Delivery, Failure, and Deduplication Behavior

| Area | Current control | Assessment |
|---|---|---|
| Reminder deduplication | Date equality only | **Insufficient**; no sent-event key or durable ledger |
| Reminder retries | None | **Insufficient**; send result is not persisted |
| Reminder scheduling | Immediate process startup plus `setInterval(24h)` | **Unreliable on autoscale** and restart-sensitive |
| Portal staff-email evidence | Outbox row before send; sent/failed status | Good evidence, but no retry processor |
| Portal push evidence | Outbox row per token | Good structure; currently unused because there are no tokens |
| Portal client deduplication | One notification per unique linked portal user | Appropriate |
| System recipient deduplication | Case-insensitive email normalization | Appropriate |
| Client preference handling | Applied to push category only | In-app notifications always persist; email preference is presently unused |
| Failure visibility | Failed portal email remains in outbox | Visible in database but not surfaced through an operations dashboard or alert |

Runtime evidence also showed the reminder check starting repeatedly whenever the development server restarted. The observed emails were from the scheduler’s non-documentation receipt reminder, but the same startup behavior applies to all Client Documentation reminder conditions. A due documentation reminder can therefore be sent more than once during restarts or multiple-instance overlap.

## Privacy and Security Controls

The system blocks internal email sending if the configured sender belongs to `@elevay.com`, uses Gmail SMTP credentials from environment secrets, and automatically includes Ziad’s Gmail on internal notifications.[2] [8] Client password-reset messages explicitly bypass internal recipient copying and are sent only to the client.[2]

Client-upload emails do not attach sensitive files; they include a protected CRM link instead.[2] The email still contains client identity, application metadata, document type, and an optional comment. Client-message alerts can contain message content, and push notifications can show message text. These contents should be treated as confidential operational data. Delivery-outbox payloads retain email HTML or push text in the database; no retention policy is currently enforced in this flow.

## Gaps Against the Required Client Documentation Contract

| Requirement | Status | Evidence |
|---|---|---|
| Notify assigned consultant | **Not met for scheduled reminders and assignment email** | Short-name/full-name mismatch; six-argument call to a two-argument function |
| Notify assigned paralegal | **Not met for scheduled reminders and assignment email** | Same defect; nine current cases also have no paralegal assigned |
| Notify Mahmoud | **Partially met** | Reminder fallback and assignment email include Mahmoud; portal staff alerts always include Mahmoud corporate address |
| Include Ziad Gmail on all internal notifications | **Met** | Central recipient merge adds the address case-insensitively |
| First notification when submission date is updated | **Not reliably met** | Daily condition check rather than event-driven notification; condition can repeat |
| Second notification before submission date | **Implemented at 12 days** | Date equality check on expected submission date |
| Include client name and code | **Partially met** | Submission reminders include both; Schengen, embassy, and document-expiry emails omit code |
| Include remaining unpaid contract amount | **Not met** | No reminder query or template includes the amount |
| Durable schedule and exactly-once delivery | **Not met** | No managed Heartbeat job, run ledger, notification ledger, or overlap claim |
| Delivery retry and operational alerting | **Not met** | One failed portal email exists; no retry worker or alert |

## Prioritized Recommendations

### Priority 1 — Correct Recipient and Assignment Defects

Create one canonical staff-name resolver that accepts both short and full names, then use it in all Client Documentation emails. Replace `notifyNewClientAssigned(clientName, assignedTo)` with a structured object containing client name, client code, application type, marital status, consultant, and paralegal. The recipients should be the assigned consultant, assigned paralegal when present, Mahmoud, and the mandatory Ziad Gmail recipient.

### Priority 2 — Replace the In-Process Reminder Timer

Move Client Documentation reminders to a managed authenticated Heartbeat callback at a fixed Cairo time. Add a durable notification ledger keyed by client/document, reminder type, and scheduled date. The handler should claim the daily run atomically, prevent overlap, retry safe failures, and record count-only results.

### Priority 3 — Implement the Submission-Date Contract Exactly

Send the first email within the transaction that updates the submission date. Send the second at the approved lead time—currently 12 days before the expected submission date. Both emails should include client name, client code, actual/expected submission date, assigned consultant, assigned paralegal, and the remaining unpaid contract amount calculated from the authoritative Financial client/receipt data.

### Priority 4 — Process Failed Delivery-Outbox Rows

Add a bounded retry worker for failed/pending Client Portal email and push rows, with exponential backoff, maximum attempts, sanitized errors, and an administrator alert after final failure. The existing failed document-upload email should be retried only after the policy is deployed and reviewed.

### Priority 5 — Restore Push Readiness and Improve Privacy

Verify the mobile app registers Expo tokens after login and refreshes them when they rotate. Add a device/notification health panel for administrators. Localize push text to the account language and use privacy-safe lock-screen wording such as “You have a new secure message” rather than including message content.

### Priority 6 — Add Focused Regression Tests and Monitoring

No focused tests currently reference the reminder scheduler, assignment notification, portal notification table, delivery outbox, or push helper. Add deterministic tests for each trigger day, recipient set, no-paralegal fallback, submission amount, duplicate prevention, outbox retry, preference suppression, Arabic push localization, and sensitive-content exclusion.

## Conclusion

Client Documentation has broad notification coverage, especially for Client Portal workflow actions, but the most business-critical email reminders are not yet reliable enough for production operations. The portal in-app system is functioning for linked cases, while push has no active delivery path today. The immediate focus should be to fix recipient resolution and new-assignment parameters, move reminders to a durable managed schedule, implement the exact submission-date/payment notification contract, and add retry/monitoring for failed outbox events.
